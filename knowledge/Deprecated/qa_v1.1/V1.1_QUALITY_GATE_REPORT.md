## 3. Verified Strengths (Selling Points)
1. **Unbreakable Session Isolation:** Cryptographic multi-tenant separation is functioning perfectly. User B cannot access User A's data under any tested adversarial condition.
2. **High-Performance Scrubbing:** The hybrid Aho-Corasick + Regex engine processes 3.5KB payloads with 200+ PII hits in **~24ms**.
3. **Exceptional Concurrency:** The standalone SQLite/Axum stack achieved **440+ RPS** during 50-concurrent-user burst tests.
4. **Dynamic Adaptability:** `rules.yaml` can be hot-reloaded seamlessly without dropping active connections.

## 4. Documented Gaps & Known Limitations (V1.1 Caveats)
*These items have been explicitly pinpointed during adversarial testing and are slated for remediation in V1.2. They do not block the V1.1 release but must be disclosed/managed.*

*   **GAP-01: Policy Enforcement Naming Sensitivity**
    *   **Description:** The current engine uses a string-matching heuristic (`rule_id.contains("block")`) to determine if a PII match should hard-block a request.
    *   **Impact:** If an administrator creates a sensitive rule but fails to include the word "block" in the ID (e.g., `us_ssn`), the system will redact it but will *not* trigger the hard-block circuit breaker.
    *   **Mitigation:** Clear documentation in the Admin Guide regarding rule naming conventions.

*   **GAP-02: Fail-Open on Audit DB Read-Only**
    *   **Description:** If the host system's disk permissions change and `audit.db` becomes read-only, the logging thread logs a critical error but the gateway *continues to process and scrub requests*.
    *   **Impact:** Compliance risk. Scrubbing occurs without a tamper-evident audit trail.
    *   **Mitigation:** Monitor the server logs for "Audit DB anchoring failure" via external SIEM.

*   **GAP-03: AMKA Date Boundary Looseness**
    *   **Description:** The Greek AMKA regex correctly identifies the format but does not strictly validate the physical possibility of the date (e.g., it will flag month "13").
    *   **Impact:** Minor False Positives in the Greek market.

*   **GAP-04: Distributed Contention (Standalone Only)**
    *   **Description:** IronWarden V1.1 is certified for **Standalone (Single Node)** deployments only. If two IronWarden processes attempt to share the same `audit.db` file, they will encounter SQLite file lock timeouts.
    *   **Mitigation:** Customers requiring HA (High Availability) load-balancing must wait for the V1.2 Redis-backed release.
